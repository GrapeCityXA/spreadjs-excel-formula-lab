# 用例设计规范

> 这份文档是项目的重点：**架构只是管道，结论的可信度取决于用例和基线。**
> 新增用例、评审用例、判断“差异是不是缺陷”时，先看这里。

这组数字是“当前语料”的覆盖，不是兼容性结论；新增用例时优先补维度分布，而不是重复刷函数个数。

## 1. 一条用例只验证一个语义点

每条用例由「一组输入 + 一个公式 + 一个读取区域」构成，只用来回答一个问题，例如：

- `SUM` 对区域内的文本数字怎么处理？
- `ROUND` 在 .5 边界怎么舍入？
- `VLOOKUP` 精确匹配遇到重复键返回哪一行？
- `DAYS` 在 1900-02-28 与 1900-03-01 之间返回 1 还是 2？

不要在一个公式里同时验证类型转换、舍入和错误传播——一旦出现差异，无法归因。

## 2. 用例维度

每个函数至少一条基线用例；核心函数按维度补深。维度是**覆盖率的第二把尺子**（第一把是函数个数）：

| 维度 | 说明 | 例子 |
| --- | --- | --- |
| 基线 | 最常见、最直观的输入 | `=SUM(A1:A4)` |
| 参数边界 | 0、负数、极大/极小、缺省参数、可选参数 | `=ROUND(2.5,0)`、`=MOD(-10,3)` |
| 类型转换 | 文本数字、布尔、空串、错误值，直接参数 vs 区域引用 | `=COUNT("2",TRUE)`、`=SUM(A1:A2)`（区域含文本） |
| 引用形态 | 区域、整列、数组常量、绝对/相对引用 | `=SUM($A$1:$A$4)`、`=SUM({1,2;3,4})` |
| 数组 / 溢出 | 动态数组、CSE、广播 | `=UNIQUE(A1:A4)` + `readRange` |
| 错误语义 | 错误码、错误传播、`IFERROR` 包裹 | `=SQRT(-1)`、`=1/0` |
| 日期 / 时间 | 1900/1904、闰年、序列值、极值 | `=DAYS(DATE(1900,3,1),DATE(1900,2,28))` |
| 文本 / 区域 | DBCS、大小写、通配符、货币/小数格式 | `=MIDB("中文文本",3,2)`、`=DOLLAR(1234.567,2)` |
| 数值精度 | 15 位有效数字、浮点边界、近似算法 | `=TINV(0.05,10)`、`=BESSELK(1,0)` |
| 查找匹配 | 精确 / 近似 / 通配符 / 重复键 / 排序假设 | `=VLOOKUP("b",A1:B3,2,FALSE)` |
| 配置 | 同一公式在 `ExcelCompatibleCalcMode` 开/关下的行为 | `=AVERAGE(2,"4")` |
| 组合 | 嵌套函数、数组公式、业务化场景 | `=IFERROR(VLOOKUP(...),0)` |

## 3. 优先级

| 优先级 | 定义 | 用法 |
| --- | --- | --- |
| `P0` | 高频函数 + 常见输入 + 结论明确 | 回归必跑，失败优先修 |
| `P1` | 边界、类型转换、配置敏感、错误语义 | 发现产品问题的主要来源 |
| `P2` | 长尾函数、极端输入、近似算法 | 覆盖完整性，结论需人工复核 |

不要用“函数个数”冒充“覆盖深度”。报告里同时展示：函数覆盖数、维度分布、P0 通过率。

## 4. 字段规范

```json
{
  "id": "PUB-MATH-003",
  "category": "数学与三角函数",
  "function": "SUM",
  "scenario": "区域中混有文本数字时是否参与求和",
  "formula": "=SUM(A1:A4)",
  "data": [[1], ["2"], [3], [4]],
  "formulaCell": "H1",
  "readRange": "H1:H1",
  "priority": "P1",
  "source": "m2-design",
  "note": "验证引用类型的文本是否被强制转换"
}
```

规则：

1. `id` 全局唯一、追加后不复用；修改用例语义时新建 ID，旧 ID 保留（回归可追溯）。
2. `data` 只能包含 number / string / boolean / null；从 A1 开始，公式引用真实坐标。
3. 公式以 `=` 开头，只用 `,` 分隔参数（数组常量内部除外）。
4. `formulaCell` 默认 `H1`，不得与数据区重叠；数组结果用 `readRange` 声明区域。
5. 期望值不写死：以 Excel 实算为基线；用例只负责“给出一组有效输入”。
6. 会返回错误的用例标 `expectError: true`，否则 Excel 的错误结果会被判为 `INVALID`。
7. 易变函数标 `volatile: true`，不参与数值断言。
8. 迭代/近似类函数可放宽 `tolerance`，但必须在 `note` 写明原因。

## 5. Excel 版本策略

- 基线固定为**执行 `npm run refresh` 的那台机器上的 desktop Excel**；版本、build、区域、日期
  系统写入 `oracle/manifest.json`，报告顶部展示。
- 用例本身不假设 Excel 版本；如果某函数是 Excel 365 才有的（如动态数组、`IMAGE`、
  `EUROCONVERT` 加载项），在 `note` 里说明，报告中会把 `#NAME?` 类差异标成环境分类，而不是
  直接判缺陷。
- 用户 Excel 版本不同时：
  - 只做 `check`：以仓库提交的基线为准，结论带基线环境指纹；
  - 做 `refresh`：生成自己的基线，结果属于该用户环境，不与仓库基线混算。
- 不在一个报告里混合多个 Excel 版本。未来如需多版本矩阵，按版本分目录、分报告。

## 6. 评审清单（新增用例必过）

- [ ] 场景一句话说清了“输入是什么、验证什么”
- [ ] 只测一个语义点，失败可归因
- [ ] 输入数据可被两侧无损写入（文本不被当数字，空串不被吞）
- [ ] 公式在 Excel 与 SpreadJS 都能解析，不依赖外部引用/定义名称/跨表
- [ ] 结果确定（非易变），跨两次运行一致
- [ ] `expectError` / `volatile` / `readRange` / `tolerance` 与实际一致
- [ ] 已在报告中确认不是 `INVALID` / `EXEC_FAIL`

## 7. 结果快照

`site/` 中提交一份可浏览的测试结果（含 `compatibility.csv` / `.json` 导出），
`oracle/` 中提交产生该结果的 Excel 基线。这样用户不装 Excel 也能复现当前结论；
换机器/换版本时，用 `refresh` 生成新的基线并重新出报告。
